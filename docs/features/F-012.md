# F-012: Shared Area Templates

## Objective

Let the GM place temporary visual area templates on the currently shown
encounter so spells and similar table moments can be seen by the GM and Player
Display without changing fog, map assets, or persisted campaign prep.

## User Value

The GM can quickly show the table where a spell or area effect applies without
using physical templates, drawing on the map image, or turning TabletopFog into
a full virtual tabletop.

## Initial Decisions Captured

- This feature is post-V1 work. `v1.0.0` has been tagged as the release
  baseline.
- Start with GM-created templates only.
- Treat templates as visual aids, not rules automation.
- Templates should be seen by the GM and Player Display when they apply to the
  currently shown encounter.
- Do not introduce player-created templates in the first slice.
- Do not introduce multiple player identities, multi-display workflows, or
  player-specific state for this work.
- Model the capability as shared area overlays or templates, not highlighted
  squares as the primary data model.
- Use map-relative geometry rather than screen coordinates.
- Keep the overlay state separate from fog state.
- Prefer temporary runtime state first; do not persist templates unless a later
  planning pass finds a clear table-use need.
- Start with visual templates instead of computing exact rules-affected grid
  squares.
- Expected shape direction includes circles, cones, and additional template
  shapes such as rectangles, lines, or polygons.

## Non-Goals

- Do not add player-originated mutations in the first slice.
- Do not add player identities, player names, private state, or per-player
  ownership.
- Do not add multi-display-specific workflow support.
- Do not add spell databases, spell rules, automatic targeting, damage,
  conditions, durations, saving throws, or effect tracking.
- Do not add tokens, initiative, dice, character sheets, rules automation,
  dynamic lighting, cloud hosting, login, or authentication.
- Do not make area templates alter fog operations.
- Do not permanently edit map images.
- Do not store campaign notes, annotations, or freeform drawings as part of
  this feature.
- Do not let opening or editing an encounter change the Player Display.

## Acceptance Notes

- The GM can create and clear one or more temporary visual templates for the
  currently shown encounter.
- Templates render over the encounter map in both GM View and Player Display.
- Templates are scoped to the encounter they were created for and do not appear
  over unrelated encounters or handouts.
- Templates are not shown while the Player Display is waiting or showing a
  handout.
- Templates do not mutate map assets, fog operations, handouts, campaign image,
  shown target, or persisted campaign metadata.
- Player Display remains display-only for the first slice.
- The exact first set of shapes, drawing interactions, colors, clear behavior,
  and rendering order must be planned before implementation.

## Affected Systems

- GM view: future drawing controls, template management, and clear behavior.
- Player view: future shared rendering only; no first-slice mutation controls.
- Local server: future runtime state and GM-only mutation routes or events.
- Map/fog rendering: future overlay layer separate from fog.
- Storage: no persistence expected for the first slice.
- Documentation: roadmap, tracker, acceptance tests, and feature records will
  need updates before implementation.

## Validation Plan

To be defined in the next planning session. Expected validation areas include
GM-only mutation authorization, Player Display read-only behavior, shown-target
scoping, map-relative rendering across zoom and pan, shape geometry, clear
behavior, reconnect behavior, and full `npm run quality`.

## Open Questions

- What is the smallest first implementation slice: one template at a time,
  multiple templates, or one active template plus clear?
- Which shapes belong in the first build slice?
- Should templates render above fog, below fog, or use different behavior for
  GM View and Player Display?
- Should templates snap to the calibrated grid, ignore the grid, or offer both
  freeform and grid-aware modes?
- Should templates clear automatically when the shown encounter changes, when
  the GM clears the shown target, or only through an explicit GM action?
- Should the GM be able to choose colors, opacity, labels, or only use one
  default visual style at first?
- Should reconnecting clients receive current runtime templates if the server
  is still running?
- Should any part of this feature persist across campaign reload or server
  restart, or should all template state remain runtime-only?
