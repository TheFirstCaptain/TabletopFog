# E-016: Split GM Client Render Responsibilities

## Summary

Extract focused GM view renderers so campaign library, encounter gallery,
handout library, and workspace tool rendering can evolve independently.

## Status

Proposed.

## Behavior to Preserve

- GM campaign library, campaign cards, metadata editing, encounter gallery,
  handout library, Encounter Workspace, Player Display URL copy, map alignment,
  fog tools, Clear Fog, Undo Fog, and shown-target controls remain visually and
  functionally unchanged.
- Existing delegated event behavior and `data-action` contracts remain intact
  unless deliberately migrated with equivalent tests.
- Browser-local GM state such as selected encounter, grid alignment, fog tool
  state, and viewport controls remains local to the tab.
- Player Display behavior is unchanged.

## Motivation

`public/gm-view.js` is the main GM DOM renderer and currently owns campaign
card rendering, encounter gallery rendering, handout rendering, workspace
rendering, fog draft UI, grid UI, shared canvas integration, messages, and
confirmations. `public/gm-controller.js` also carries workflow-specific render
selection logic.

This is still workable for the current plain-JS app, but future UI work will
be safer if repeated surfaces have smaller, named render modules with narrower
inputs and tests.

## Scope

- In scope:
  - Extract focused render helpers or modules for stable GM surfaces.
  - Keep `createGmView()` as the composition boundary exposed to the
    controller.
  - Preserve the shared canvas renderer boundary.
  - Keep extraction incremental and compatible with existing browser tests.
- Out of scope:
  - Rewriting the GM client in a frontend framework.
  - Redesigning the UI.
  - Changing API calls or server behavior.
  - Changing player rendering.

## Affected Systems

- GM view: render module extraction and composition changes.
- Player view: no direct change.
- Local server: no expected change.
- Storage: no change.
- Tests and tooling: browser workflow coverage and module baseline updates.
- Documentation: this engineering record, tracker, and module responsibilities.

## Implementation Notes

Prefer incremental extraction over a broad rewrite. Good first candidates are
pure-ish render sections that already have clear container roots:

- campaign library cards
- encounter gallery cards
- handout library cards
- workspace status and tool controls

Keep event wiring in `gm-events.js` unless a specific extracted component needs
a better local event adapter. Avoid changing CSS selectors unless the browser
tests and accessibility labels are updated deliberately.

## Validation Plan

- Existing Chromium GM workflows for campaign, encounter, handout, workspace,
  fog, and shown-target behavior.
- Focused browser assertions for any surface whose DOM construction moves.
- `npm run modules:check`.
- `npm run quality`.
