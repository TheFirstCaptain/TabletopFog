# E-015: Extract Server Mutation Orchestration

## Summary

Move campaign mutation orchestration out of the Express route registry so HTTP
handlers stay focused on request parsing and response shaping.

## Status

Done.

## Behavior to Preserve

- Existing GM API routes, request formats, response formats, status codes, and
  error messages remain compatible unless a separate bug or feature explicitly
  changes them.
- GM-only mutation guards remain in place.
- Campaign, map, handout, shown-target, shown-handout rotation, fog append,
  batch fog append, Clear Fog, and Undo Fog behavior remain unchanged.
- Socket.IO broadcasts continue to send the same role-projected state after
  successful mutations.
- Legacy compatibility routes keep their current behavior while they exist.

## Motivation

`server/http-routes.js` now registers routes, validates request bodies,
coordinates storage mutations, updates the runtime state store, triggers
broadcasts, maps domain errors to HTTP responses, and carries compatibility
behavior. That keeps the app simple, but it makes each new server-side workflow
pay integration cost in one large module.

The clearest pressure is in fog and shown-target routes, where handlers
manually sequence storage writes, state-store updates, undo preservation, and
state broadcasts. A small service boundary would make those workflows easier to
test directly and would reduce future route growth.

## Scope

- In scope:
  - Extract a focused service module for campaign/session mutation workflows.
  - Keep route handlers thin: parse input, call service, return response.
  - Preserve existing storage and state-store public behavior unless the
    extraction exposes a narrow internal helper worth moving.
  - Add focused service tests for successful mutation sequencing and failure
    preservation where useful.
- Out of scope:
  - Changing product behavior.
  - Adding authentication or a new role model.
  - Replacing local JSON storage.
  - Removing compatibility API routes.

## Affected Systems

- GM view: no product change; existing API calls should continue to work.
- Player view: no product change; projected updates should remain identical.
- Local server: `server/http-routes.js` and the new service boundary.
- Storage: no storage format change.
- Tests and tooling: focused route and service coverage, existing full quality
  gate.
- Documentation: this engineering record, tracker, and module baseline updates.

## Implementation Notes

Start with the highest-churn workflows: shown-target mutations and fog
operations. Keep the route-level error mapping conservative at first, then move
shared error mapping only if repetition remains obvious.

The service should receive injected `campaignStorage`, `stateStore`, and
`onStateChange` dependencies so existing server composition and tests stay
simple. Avoid introducing a generic command framework.

## Implementation Notes

Completed on 2026-08-01.

- Added `server/campaign-session-service.js` as the injected service boundary
  for campaign/session mutation orchestration.
- Kept `server/http-routes.js` responsible for Express route registration,
  request parsing, response shaping, and conservative HTTP error mapping.
- Moved storage, runtime state-store update, undo-preservation, and broadcast
  sequencing for campaign open/create/delete, map and handout mutations,
  shown-target changes, shown-handout rotation, legacy active-map changes, and
  fog append, batch append, clear, and undo operations into the service.
- Preserved the existing campaign metadata route behavior: metadata writes
  update storage and the HTTP response without refreshing the currently open
  runtime campaign state.
- Updated the module baseline to add the new service module and ratchet
  `server/http-routes.js` down after extraction.
- README sweep: no update needed because commands, setup, runtime assumptions,
  validation workflow, and user-facing behavior did not change.
