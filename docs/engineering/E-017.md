# E-017: Add Module Cohesion Review Guidance

## Summary

Extend the module maintenance process so responsibility drift is tracked, not
only physical line-count growth.

## Status

Done.

## Behavior to Preserve

- The existing module baseline ratchet continues to block unreviewed production
  JavaScript module growth.
- Current validation commands and quality-gate behavior remain unchanged unless
  a later implementation deliberately updates documentation and tests.
- No product behavior changes.

## Motivation

The module baseline is useful because it records production JavaScript modules,
responsibilities, and physical line counts. It does not by itself flag modules
whose responsibilities become too broad while staying under the line-count
baseline.

Recent architecture review found that several modules are intentionally doing a
lot of work. Some of those are acceptable for the current app, but future
maintenance should have a clear way to record cohesion concerns and schedule
splits before they become risky.

## Scope

- In scope:
  - Define review guidance for broad module responsibilities.
  - Decide whether cohesion concerns belong in the existing module baseline,
    separate engineering records, or both.
  - Add lightweight checks or documentation only where they provide actionable
    signal.
  - Update existing module responsibility records when splits land.
- Out of scope:
  - Enforcing arbitrary maximum line counts.
  - Requiring framework-level architecture changes.
  - Reclassifying product features as maintenance work.

## Affected Systems

- GM view: no direct product change; may guide future splits.
- Player view: no direct product change.
- Local server: no direct product change; may guide future splits.
- Storage: no direct product change.
- Tests and tooling: module baseline policy and harness guidance if changed.
- Documentation: engineering tracker, module baseline guidance, and related
  maintenance records.

## Implementation Notes

Keep this process lightweight. The goal is to make broad responsibilities
visible and actionable, not to create a second lint system that blocks
reasonable small changes.

Baseline entries may include an optional `cohesionPressure` object for modules
whose current responsibility description is intentionally broad enough to need
scheduled follow-up. Use it only when there is a concrete maintenance record,
not for speculative cleanup.

Required fields:

- `engineeringId`: the active `E-NNN` record that owns the follow-up.
- `reason`: the current responsibility drift or coupling pressure.
- `plannedSplit`: the intended boundary change or review outcome.

Do not use `cohesionPressure` as a waiver for physical line-count growth. The
line ratchet still applies. When the split or review lands, update the module
responsibility text and remove or revise the cohesion-pressure reference in the
same change.

Current broad modules without an active split record remain documented by their
responsibility text alone. Create a new engineering record before adding a
cohesion-pressure reference.
