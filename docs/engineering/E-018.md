# E-018: Harden GM Role Authorization

## Summary

Record the future need to replace route/referer-based GM role checks with a
lightweight authorization boundary if TabletopFog moves beyond trusted local
LAN use.

## Status

Deferred.

## Behavior to Preserve

- Current V1 trusted-LAN setup remains lightweight.
- `/gm` continues to serve the controlling GM View.
- `/player` continues to serve the read-only Player Display.
- Player Display UI remains unable to mutate session state.
- No login, cloud accounts, or internet-hosted session model is introduced
  while the app remains scoped to trusted local-table use.

## Motivation

The current role model is intentionally simple: GM and player roles are
route-based, and server-side mutation guards infer the role from request
context. This matches the current trusted same-LAN architecture, but it is not
a real authorization boundary.

If the app is ever used outside a trusted LAN, exposed through a tunnel, hosted
remotely, or used with untrusted devices on the same network, a user who can
reach the GM route could attempt GM actions. That risk should stay visible
without adding premature setup friction to the local-table workflow.

## Scope

- In scope:
  - Revisit GM authorization when the deployment or trust model changes.
  - Evaluate lightweight options such as a GM session token, setup code,
    pairing flow, or role-specific local secret.
  - Apply the chosen boundary consistently to HTTP mutation routes and
    Socket.IO role assignment.
  - Preserve the Player Display's read-only UI and projected state behavior.
- Out of scope while deferred:
  - Login or user accounts.
  - Cloud session rooms.
  - Internet-hosted play.
  - Full multi-user permission management.
  - Changing the current V1 local-table setup.

## Affected Systems

- GM view: future setup or session token handling if the trigger occurs.
- Player view: future player connection or pairing flow only if needed.
- Local server: role detection, mutation guards, and Socket.IO role assignment.
- Storage: no expected storage format change unless a local secret is persisted.
- Tests and tooling: route, Socket.IO, and browser workflow coverage for the
  chosen authorization boundary.
- Documentation: architecture, development/setup guidance, decisions, and
  security/network troubleshooting if the trust model changes.

## Implementation Notes

Do not implement this while TabletopFog remains a trusted same-LAN tool. The
current route-based model is an intentional V1 tradeoff, documented in the
architecture and decision records.

Reopen this record before any of these triggers:

- Remote access, tunneling, or internet-hosted deployment is introduced.
- The app is expected to run on untrusted shared networks.
- Player devices are no longer assumed to be trusted table devices.
- A future feature exposes more sensitive campaign data or broader mutation
  capability over the network.

When reopened, prefer the smallest mechanism that provides a real boundary for
the updated trust model.

## Validation Plan

Deferred until the trigger occurs. Expected validation when implemented:

- Node tests proving unauthenticated or player-authenticated requests cannot
  call GM mutation routes.
- Socket.IO tests proving player connections receive only player projections
  and cannot self-assign GM role.
- Browser workflow tests proving normal GM and Player Display setup still works.
- `npm run quality`.
